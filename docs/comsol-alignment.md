# What was measured against COMSOL, and what it says

The library is meant to behave like the BDF time stepping of COMSOL's
Time-Dependent Solver. This is the measurement of how far it does, on a model
whose exact solution is known, so that nothing but the step control is compared.

## The model

A Global Equation `u + u' = 0`, `u(0) = 1`, over `[0, 10] s`: one degree of
freedom, a linear equation, an exact solution. The COMSOL model is generated by
`tools/comsol/AtsReference.java` and run by `tools/comsol/run.py`; the solver's
own steps are read back by storing "Steps taken by solver" and exporting the
solution, and its log by setting `keeplog` and reading the solver message back.
The recorded steps are in `test/reference/comsol_steps.hpp`.

The settings were read back from the solver node of that model, not assumed:

| Property | Value | The library's setting |
| --- | --- | --- |
| `timemethod` | `bdf` | — |
| `tstepsbdf` | `free` (also `intermediate`, `strict`, `manual`) | `step_mode` |
| `tout` | `tlist` (also `tstepsclosest`, `tsteps`) | `store_mode` |
| `maxorder` | 5 | `max_order` |
| `minorder` | 1 | `min_order` |
| `bdforder` | 2 | `manual_order` |
| `rtol` | 0.01 | `relative_tolerance` |
| `atolglobalvaluemethod` / `atolglobalfactor` | `factor` / 0.1 | `absolute_factor` |
| `atolglobalmethod` | `scaled` | `scale_absolute_tolerance` |
| `initialstepbdf` / `initialstepbdfactive` | 0.001 / off | `first_step_fraction` |
| `maxstepconstraintbdf` / `maxstepbdf` | `auto` / 0.1 | `max_step_fraction` |
| `endtimeinterpolation` | on | `interpolate_end_time` |
| `consistent` / `bwinitstepfrac` / `bwinitfactor` | `bweuler` / 0.001 / 20 | `init_step_fraction` |
| `eventtol` | 0.01 | out of scope |

COMSOL's documentation names its BDF solver: IDA, of SUNDIALS, "a modernized
implementation of the DAE solver DASPK, which uses variable-order
variable-step-size backward differentiation formulas", with orders "from one to
five". That is the algorithm this library implements, from the source of
`IDASetCoeffs`, `IDATestError`, `IDAHandleNFlag` and `IDACompleteStep`.

## The startup agrees, step for step

COMSOL's stored times of the default run are

```text
0  0.00602  0.01202  0.02402  0.04802  0.09602  0.19202  0.38402  0.57602  ...
```

and the steps between them, with the first entry holding the state its
consistent initialization left at `t = 0`:

```text
0.00602  0.006  0.012  0.024  0.048  0.096  0.192  0.192  0.192  0.192  0.384  ...
```

The library, with the same settings, takes

```text
0.006  0.006  0.012  0.024  0.048  0.096  0.192  ...
```

One order higher and twice the size per step — IDA's startup phase, which
COMSOL's log shows as the steps 0.006, 0.006, 0.012, 0.024, 0.048 s at the
orders 1, 1, 2, 3, 4. The same alignment holds for the other tolerances, scaled
by the tolerance: `rtol = 1e-3` puts the sequence at 0.0006, 0.0006, 0.0012, ...,
`rtol = 1e-5` at 6e-6, 6e-6, 1.2e-5, ... — both COMSOL's and this library's.

## The step counts

Ten configurations of the same model, and the accepted steps each run took
(COMSOL's stored times less its initial state):

| Configuration | COMSOL | AdaptiveTimeStepper | Difference |
| --- | --- | --- | --- |
| default (orders 1–5, rtol 1e-2) | 37 | 29 | −22 % |
| maximum BDF order 1 | 108 | 63 | −42 % |
| maximum BDF order 2 | 58 | 38 | −35 % |
| maximum BDF order 3 | 39 | 30 | −23 % |
| maximum BDF order 4 | 39 | 29 | −26 % |
| rtol 1e-3 | 60 | 43 | −28 % |
| rtol 1e-5 | 98 | 75 | −24 % |
| steps taken by solver: strict | 49 | 41 | −16 % |
| steps taken by solver: intermediate | 37 | 29 | −22 % |
| maximum step constant 0.05 s | 204 | 204 | 0 % |

Two of them agree exactly, the maximum step among them — where the step is the
constraint's and not the controller's. The rest differ by 16 to 42 %, always in
the same direction: this library takes *fewer*, larger steps than COMSOL after
the startup.

## Why it does not agree exactly

The startup is deterministic — one order higher and twice the size — so it
agrees by construction. What follows depends on the local error estimate, and
the two are not the same quantity even though they come from the same algorithm.

**The estimate.** IDA keeps its history as a Nordsieck-like array of scaled
derivatives `phi[j] = h^j y^(j)/j!` and forms the correction `ee` against the
predictor `sum phi[0..k]`. This library keeps the time levels themselves and
forms the correction against the polynomial through the last `k + 1` levels,
which is the same polynomial — the two agree to round-off — but the estimates at
the *other* orders differ in their constants:

- IDA's estimate at the order below is `||phi[k] + ee||`, its `phi[k]` being the
  scaled component it accumulated and re-scaled with its step-ratio `beta`;
- this library's is `||y - p_{k-1}||`, the same quantity computed from the levels
  directly.

They differ by the re-scaling, and a step-size change is exactly when it
matters. Since the startup doubles the step every step, every estimate of the
first half of a run is formed across a step-size change.

**The consequences.** COMSOL's order settles at 2 or 3 on this model and holds a
step for several steps in the deadbeat band; this library's settles higher —
4 or 5 — because its `terr_km2` (the estimate two orders below) is larger, which
suppresses the decrease IDA takes. A higher order means a smaller estimate, a
larger step, and fewer steps — the 20 to 40 % above.

**What this is not.** It is not a difference of tolerances (the first steps agree
exactly), of the modes (they agree), of the maximum step (it agrees), or of the
order range (it agrees). It is the shape of the estimate at the orders a step was
not taken at, and of the order selection that reads it.

## The tolerance: the first step pins it down

The first step of a run is `min(1e-3 span, 0.5 / ||y'||_w)`, and the derivative
of this model is `-1` at a state of `1`, so the first step is the second term
alone and it measures the tolerance:

| Absolute tolerance | `A + R |y|` at `y = 1` | First step |
| --- | --- | --- |
| `A = R * factor` = 0.001 | 0.011 | 0.0055 |
| `A = R * factor * (beta + ||y||_2)` = 0.002 | 0.012 | 0.006 |

COMSOL's first step is 0.006, so its absolute tolerance is the *scaled* form,
0.002 for a state of order one — which is why `scale_absolute_tolerance`
defaults to true and reproduces 0.006 exactly. The plain form is available and is
what a run of a physical field of large magnitude is easier to reason about
with.

## Reproducing the measurement

```text
python tools/comsol/run.py --write-reference     # needs comsolcompile/comsolbatch
ctest --test-dir build -R atstep_tests
```

`test/reference/test_comsol_ode.cpp` replays each configuration and checks three
things: that the first six steps are COMSOL's to 0.1 %, that the step count is
within a factor of two of COMSOL's (the band this document explains), and that
the counts are exactly the ones this library produced when the reference was
recorded — the regression that catches an unintended change of the control.

## What is not covered

- A model with more than one degree of freedom. The norm is the mean square over
  the whole state, so the comparison above says nothing about how COMSOL's
  per-variable weighting of a coupled solve behaves; the library takes the norm
  as a template parameter for exactly that reason.
- A nonlinear solve. The model is linear, so the correction `ee` is the
  truncation error and not an iteration error.
- Generalized alpha, events, and the algebraic-variable handling of the error
  test (`estrat`). Out of scope.
